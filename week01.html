Workshop registration case study and test lab

A community workshop has limited places. Your team has been asked whether its registration app is ready to release. Read the rules, predict what should happen, then use the demo to gather evidence. Use made-up names and email addresses. The demo does not submit real registrations or send email.

Opening vote

One normal booking for one place passed. Is that enough evidence to release the app? Record your team's answer and one reason. Return to it at the end.

L01 Activity 1: Testing across development

Map the product owner, analyst, designer, developer, tester, and user across planning, design, build, release, and maintenance. At which two stages would you ask a testing question, and what would you ask? Record your answers in the L01 worksheet or your own notes.

L01 Activity 2: What could go wrong?

Rank these incidents for the workshop service. For your top two, identify who is affected, the consequence, and a test that might have found the problem.

  1. Four people receive confirmed places when only three remain. One arrives and is turned away.
  2. A confirmation is accepted with an email address that cannot receive mail. The learner misses joining details.
  3. After a cancellation, the site still shows no places. A waiting learner cannot register.
  4. A discount is applied incorrectly, so some learners pay more than the displayed price.

L01 Activity 3: Acceptance rules

  1. R1: The workshop starts with 3 places available.
  2. R2: A request for 1 to 3 places succeeds only when enough places remain. A request that exceeds availability is rejected.
  3. R3: The learner must supply a name and an email in the form name@domain.tld.
  4. R4: One email address may have only one active booking.
  5. R5: Each place costs S$20. The code STUDENT gives 10% off the total.
  6. R6: Cancelling a booking releases its places for others.

    L01 team tasks

    1. Before testing

    Choose two rules. For each, predict an input and the result you expect. Include one unusual or boundary input.

    2. While testing

    Run at least two tests per person. Record the input, what the app did, and whether that matched the rule. Reset when you need a clean starting state.

    3. Report a finding

    Give the rule number, steps to reproduce, expected result, actual result, and possible impact on a learner or the provider.

    4. Release decision

    Which issue would you fix first, and why? What question would remain unanswered even if every test you tried passed?

    L02 Activity 1: Seven testing principles

    Use the seven principles in your L02 worksheet. Match each clue below to a principle, then write one action a tester should take. You may use evidence from the demo.

    1. The team repeats only the same normal booking every week and stops finding problems.
    2. The team lists hundreds of possible quantities, emails, discount codes, and booking histories. There is not enough time to try every combination.
    3. Several checks passed. A manager says this proves the app has no defects.
    4. A workshop booking tool and an emergency appointment system need different testing priorities.
    5. Before development, the team notices that “valid email” was never defined clearly.
    6. Every written check passes, but learners say the service does not help them register in the way they need.
    7. Most reported issues come from the booking and cancellation part of the app.

    L02 Activity 2: Test process

    Match each project task to one of the seven test-process activities in your L02 worksheet. Put the main activities into a useful working order. Which activity happens throughout rather than only once?

    1. Run a prepared check, compare actual with expected, and log the result.
    2. Agree on objectives, scope, priorities, people, and the approach.
    3. Summarise results, close the testing work, and retain useful test materials.
    4. Review the rules and identify what needs testing.
    5. Check progress against the plan and adjust work when needed.
    6. Prepare test data, procedures, and an environment ready for testing.
    7. Choose how to test each condition and define expected results.

    Exit ticket

    In your worksheet or notes, record one objective of testing, one principle that changed how you tested, and one test-process activity you performed in the lab.
